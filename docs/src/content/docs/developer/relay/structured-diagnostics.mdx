The relay emits structured logs for operator diagnosis without retaining message content or authentication material. Under protocol v2 ([online relay authentication v2](../../protocol/online-relay-auth-v2/)) the only credential is one optional static shared secret checked at the HTTP upgrade, so no pairing, key, challenge, or signature event exists. Normal server events go to the server process's stdout. Fatal server startup or runtime failure goes to server stderr as `server_failed`. Extension events go to the Pi process's stderr through `console.error`, except that the interactive TUI never receives them on stderr — a persisted TUI session appends every event to its own JSONL log file, and headless hosts keep the stderr stream as their record. Every nonempty line is exactly one JSON object; event values are JSON-escaped and never create a second physical line.

<Decision title="Keep diagnostics in two process-owned JSONL streams" status="accepted">
The server owns authoritative protocol and delivery outcomes on stdout. The extension owns Pi-session, reconnect, and model-tool outcomes on Pi stderr. This preserves settlement authority while allowing operators to correlate both sides without a logger framework, exporter, or new protocol surface.
</Decision>

<Decision title="Persisted TUI sessions capture per-session files; headless hosts keep stderr" status="accepted">
The interactive TUI mutes stderr diagnostics, so its record lives in one JSONL file per persisted session at `~/.local/state/pi-messaging-relay/sessions/<session-file>.log.jsonl` (`PI_MESSAGING_RELAY_LOG_DIR` overrides the directory; `XDG_STATE_HOME` is honored). Appends are fire-and-forget single `O_APPEND` writes with no locking or fsync — one session owns one file, so no cross-session synchronization exists — and the in-session `/relay-logs` command tails the newest 200 lines on demand. Headless hosts (rpc, print, json) and in-memory sessions capture no file: their stderr stream is the record, and `/relay-logs` reports exactly that instead of inventing a capture.
</Decision>

## Severity and event vocabulary

`info` records normal transitions and completed operations. `warn` records a recoverable rejection, retry exhaustion, denied or timed-out extension tool result, or local operation failure. `error` is reserved for `server_failed`, where startup or runtime cannot continue safely. A server `send_settled` remains informational even when its protocol status is `timeout`: it authoritatively records a completed sender result rather than a relay process fault. The extension reports the same non-received tool outcome at `warn` because the caller's requested operation did not reach `received`.

### Server stdout

| Event | Level | Stable fields beyond `level` and `event` |
|---|---|---|
| `server_ready` | `info` | `result: "ready"`, `address`, `state_dir`, `auth: "off" \| "secret"` |
| `auth_accepted` | `info` | `result: "accepted"`, hello `request_id`, address, route, hostname, cwd, `latency_ms` |
| `auth_rejected` | `warn` | `result: "rejected"`, `reason`, `latency_ms`; post-hello rejections add the available route and hello `request_id` |
| `session_disconnected` | `info` | `result: "disconnected"`, address, route |
| `operation_settled` | `info` | `result`, `reason`, `code`, `type`, request correlation and outcome-specific fields, `latency_ms` |
| `operation_denied` | `warn` | `result: "denied"`, `reason`, `code`, `type`, available correlation and route fields, `latency_ms` |
| `send_settled` | `info` | `result: "settled"`, `reason`, `code`, request/message correlation, available delivery and routes, `status`, `body`, `latency_ms` |
| `server_stopped` | `info` | `result: "graceful"`, `address` |

`session_capacity_rejected` and `protocol_rejected` are recoverable server warnings with stable `result` and stable `reason`/`code` as applicable. An upgrade rejection before any WebSocket exists is `auth_rejected` with `reason: "not_authorized"` and no request or route field; post-hello rejections (`invalid_hello`, `route_conflict`, `welcome_failed`) add the hello request ID when available.

### Extension stderr

Per-session JSONL capture mirrors this table exactly: the file stores the same one-object-per-line events, in emit order, that stderr hosts receive. The `/relay-logs` command reads the newest 200 lines of the current session's file; headless hosts and in-memory sessions have no file, so the command reports that their stderr stream is the record.

| Event | Level | Stable fields beyond `level` and `event` |
|---|---|---|
| `relay_session_started` | `info` | `result: "started"`, normalized lifecycle `reason`, `route_id` |
| `relay_config_rejected` | `warn` | `result: "rejected"`, `reason`, `secret: "<redacted>"` |
| `relay_auth_accepted` | `info` | `result: "accepted"`, address, route, `latency_ms` |
| `relay_auth_rejected` | `warn` | `result: "rejected"`, `reason`, available route, available `latency_ms` |
| `relay_session_disconnected` | `info` | `result: "disconnected"`, available reason, address, route |
| `relay_reconnect_scheduled` | `info` | `result: "scheduled"`, bounded `reason`, one-based `retry_index`, `delay_ms`, route |
| `relay_reconnect_attempted` | `info` | `result: "attempted"`, one-based `retry_index`, route |
| `relay_reconnect_succeeded` | `info` | `result: "connected"`, one-based `retry_index`, address, route, `latency_ms` |
| `relay_reconnect_exhausted` | `warn` | `result: "exhausted"`, bounded `reason`, `retry_index: 10`, route |
| `relay_send_settled` | `info` for `received`; otherwise `warn` | `operation: "agent_send"`, `result: "settled"`, `reason`, `message_id`, authenticated `sender_route`, requested `recipient_route`, `status`, `body`, `latency_ms` |
| `relay_operation_failed` | `warn` | `operation`, `result: "failed"`, `reason`, plus safe operation-specific route, redaction, and latency fields when available |
| `relay_session_stopped` | `info` | `result: "graceful"`, optional address and route |

Startup-owned connection success uses `relay_auth_accepted`. A successful automatic retry uses `relay_reconnect_succeeded` instead; emitting both would duplicate one extension-owned state transition. Server `auth_accepted` still records every accepted WebSocket because the server owns that authentication boundary.

## Redaction and availability

The literal marker is `<redacted>`. Whenever these fields are emitted, `secret` and `body` contain only that marker. This applies to successful and rejected operations. The shared secret exists only in the server's secret file and the client's config file, both mode `0600`, and never enters any event beyond the redacted `secret` field. String bodies, object members, rendered provenance text, and semantic fingerprints never enter logs. Hostile body objects are validated and encoded before transport. Failure diagnostics snapshot operation inputs once, admit only a primitive string as optional recipient metadata, and never pass a body or cast parameter object into event serialization. A `toJSON` method, proxy trap, circular value, or line break therefore cannot make diagnostic encoding expose object-derived content or replace operation ownership.

Complete opaque route addresses, cwd, hostname, and request/message/delivery IDs remain visible. They are support correlation values, not authorization evidence. The server authenticates from the configured upgrade secret, never from visible route metadata.

The extension's retained authenticated connection owns its local `sender_route`; the model-tool boundary owns the generated logical `message_id` and validated requested `recipient_route`. `relay_send_settled` publishes all three. It does not receive the server-generated `delivery_id`, and its public tool wrapper does not own the transport's per-frame `request_id`; it therefore publishes neither. The authoritative server `send_settled` publishes request and delivery IDs when that outcome has them. Server authentication publishes the hello `request_id` after a complete hello is available; upgrade rejections happen before any hello and publish none. No identifier is lifted through an internal abstraction solely for logging.

<Aside type="note" title="Heartbeat control traffic stays quiet">
The welcome value `heartbeat_ms: 30000` is transport metadata. WebSocket ping/pong control traffic produces no normal-level heartbeat, ping, or pong event. Disconnect and reconnect transitions provide actionable evidence without one log per control tick.
</Aside>

## Support correlation workflow

1. Start with the extension's `relay_send_settled.message_id`, authenticated `sender_route`, and requested `recipient_route`.
2. Find the server `send_settled` with the same `message_id` and sender/recipient route. Use its `request_id` and, when present, `delivery_id` to inspect transport-side outcomes.
3. Match route across `relay_auth_accepted` or `relay_reconnect_succeeded` and server `auth_accepted`.
4. For an interruption, follow `relay_session_disconnected` to `relay_reconnect_scheduled`, `relay_reconnect_attempted`, and `relay_reconnect_succeeded`. `retry_index` is one-based and `delay_ms` is the actual jittered wait.
5. Share identifiers only with a trusted support channel. Never share the server secret file, the client config file, or message content.

## Captured-stream acceptance

The primary diagnostics case in `extension/test/connect.acceptance.test.ts` builds and starts the real Go child and captures its stdout JSONL and the extension's actual stderr bytes. One variant starts the server with `--secret-file`, loads the extension with a mode-`0600` client config file carrying the same secret, and proves the full boundary: `server_ready` reports `"auth":"secret"`, the configured session upgrades and authenticates, and every wrong credential spelling — missing header, wrong scheme, wrong secret — receives the identical closed HTTP 401 without an upgrade or tracked slot. A second variant boots the server without a secret and proves `"auth":"off"` accepts header-less and credentialed clients identically with no rejection event.

The case requires the exact four-event connected session lifecycle (`relay_session_started`, `relay_auth_accepted`, `relay_session_disconnected`, `relay_session_stopped`), the reconnect event order under the fake-clock retry controls, message correlation between `relay_send_settled` and server `send_settled`, and the severity split between informational settlements and warning tool outcomes. Every captured nonempty line must parse as one non-array JSON object with no embedded physical newline; extension lines come from actual stderr bytes, not captured console arguments. No captured server or extension line may contain the secret value, and any `secret` field must carry the literal `<redacted>` marker. No `client_public_key`, `nonce`, `signature`, or `client_id` field may appear in any v2 event. Sibling acceptance cases (`delivery.acceptance.test.ts`, `roster.acceptance.test.ts`, `reconnect.acceptance.test.ts`, `restart.acceptance.test.ts`) prove settlement, roster, bounded reconnect, and process-replacement behavior over the same captured streams, including one warning-level `relay_reconnect_exhausted` after ten failed retries and no eleventh retry.

<Decision title="Use logs only for relay observability" status="accepted">
The operator-run relay has no demonstrated SLO, throughput, or cross-process complexity requiring OpenTelemetry. The relay adds no metrics, traces, exporter, collector, health API, or dependency. Revisit only when measured operational needs cannot be answered from bounded structured events.
</Decision>
