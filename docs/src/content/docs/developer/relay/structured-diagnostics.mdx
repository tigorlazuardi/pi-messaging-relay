Relay v1 emits structured logs for operator diagnosis without retaining message content or authentication material. Normal server events go to the server process's stdout. Fatal server startup or runtime failure goes to server stderr as `server_failed`. Extension events go to the Pi process's stderr through `console.error`. Every nonempty line is exactly one JSON object; event values are JSON-escaped and never create a second physical line.

<Decision title="Keep diagnostics in two process-owned JSONL streams" status="accepted">
The server owns authoritative protocol and delivery outcomes on stdout. The extension owns Pi-session, reconnect, and model-tool outcomes on Pi stderr. This preserves settlement authority while allowing operators to correlate both sides without a logger framework, exporter, or new protocol surface.
</Decision>

## Severity and event vocabulary

`info` records normal transitions and completed operations. `warn` records a recoverable rejection, retry exhaustion, denied or timed-out extension tool result, or local operation failure. `error` is reserved for `server_failed`, where startup or runtime cannot continue safely. A server `send_settled` remains informational even when its protocol status is `timeout`: it authoritatively records a completed sender result rather than a relay process fault. The extension reports the same non-received tool outcome at `warn` because the caller's requested operation did not reach `received`.

| `pair_rejected` | `warn` | `result: "rejected"`, `reason`, `latency_ms`, available public key, redaction fields |
| `auth_accepted` | `info` | `result: "accepted"`, validated hello `request_id`, address, route, public-key/client identity, hostname, cwd, `latency_ms`, redaction fields |
| `auth_rejected` | `warn` | `result: "rejected"`, `reason`, available route/public key and validated hello `request_id`, `latency_ms`, redaction fields |
| `session_disconnected` | `info` | `result: "disconnected"`, address, route, public-key/client identity |
| `operation_settled` | `info` | `result`, `reason`, `code`, `type`, request correlation and outcome-specific fields, `latency_ms` |
| `operation_denied` | `warn` | `result: "denied"`, `reason`, `code`, `type`, available correlation and route fields, `latency_ms` |
| `send_settled` | `info` | `result: "settled"`, `reason`, `code`, request/message correlation, available delivery and routes, `status`, `body`, `latency_ms` |
| `server_stopped` | `info` | `result: "graceful"`, `address` |

`session_capacity_rejected` and `pairing_code_channel_cleanup_failed` are recoverable server warnings with stable `result` or `reason` as applicable. Protocol rejection is `protocol_rejected` with `result: "rejected"`, stable `reason` and `code`, and only validated correlation safe to publish.

### Extension stderr

| Event | Level | Stable fields beyond `level` and `event` |
|---|---|---|
| `relay_session_started` | `info` | `result: "started"`, normalized lifecycle `reason`, `route_id` |
| `relay_pair_accepted` | `info` | `operation: "relay-pair"`, `result: "accepted"`, public-key/client identity, `latency_ms`, redaction fields |
| `relay_pair_rejected` | `warn` | `operation: "relay-pair"`, `result: "rejected"`, `reason`, `latency_ms`, redaction fields |
| `relay_auth_accepted` | `info` | `result: "accepted"`, address, route, public key, `latency_ms`, redaction fields |
| `relay_auth_rejected` | `warn` | `result: "rejected"`, `reason`, available route/public key, available `latency_ms`, redaction fields |
| `relay_session_disconnected` | `info` | `result: "disconnected"`, address, route, public key, redaction fields |
| `relay_reconnect_scheduled` | `info` | `result: "scheduled"`, bounded `reason`, one-based `retry_index`, `delay_ms`, route, public key |
| `relay_reconnect_attempted` | `info` | `result: "attempted"`, one-based `retry_index`, route, public key |
| `relay_reconnect_succeeded` | `info` | `result: "connected"`, one-based `retry_index`, address, route, public key, `latency_ms` |
| `relay_reconnect_exhausted` | `warn` | `result: "exhausted"`, bounded `reason`, `retry_index: 10`, route, public key |
| `relay_send_settled` | `info` for `received`; otherwise `warn` | `operation: "agent_send"`, `result: "settled"`, `reason`, `message_id`, authenticated `sender_route`, requested `recipient_route`, `status`, `body`, `latency_ms` |
| `relay_operation_failed` | `warn` | `operation`, `result: "failed"`, `reason`, plus safe operation-specific route, redaction, and latency fields when available |
| `relay_session_stopped` | `info` | `result: "graceful"`, available address, route, and public key |

Initial and pairing-owned authentication success uses `relay_auth_accepted`. A successful automatic retry uses `relay_reconnect_succeeded` instead; emitting both would duplicate one extension-owned state transition. Server `auth_accepted` still records every accepted WebSocket because the server owns that authentication boundary.

## Redaction and availability

The literal marker is `<redacted>`. Whenever these fields are emitted, `pairing_code`, `nonce`, `signature`, `private_key`, and `body` contain only that marker. This applies to successful and rejected operations. String bodies, object members, rendered provenance text, and semantic fingerprints never enter logs. Hostile body objects are validated and encoded before transport. Failure diagnostics snapshot operation inputs once, admit only a primitive string as optional recipient metadata, and never pass a body or cast parameter object into event serialization. A `toJSON` method, proxy trap, circular value, or line break therefore cannot make diagnostic encoding expose object-derived content or replace operation ownership.

Public Ed25519 keys, client IDs, complete opaque route addresses, cwd, hostname, and request/message/delivery IDs remain visible. They are support correlation values, not authorization evidence. The server authenticates from its allowlist and verified signature, never from visible route metadata.

The extension's retained authenticated connection owns its local `sender_route`; the model-tool boundary owns the generated logical `message_id` and validated requested `recipient_route`. `relay_send_settled` publishes all three. It does not receive the server-generated `delivery_id`, and its public tool wrapper does not own the transport's per-frame `request_id`; it therefore publishes neither. The authoritative server `send_settled` publishes request and delivery IDs when that outcome has them. Server authentication publishes the validated hello `request_id` after a complete hello is available; challenge-write and incomplete-hello failures omit it. No identifier is lifted through an internal abstraction solely for logging.

<Aside type="note" title="Heartbeat control traffic stays quiet">
The welcome value `heartbeat_ms: 30000` is transport metadata. WebSocket ping/pong control traffic produces no normal-level heartbeat, ping, or pong event. Disconnect and reconnect transitions provide actionable evidence without one log per control tick.
</Aside>

## Support correlation workflow

1. Start with the extension's `relay_send_settled.message_id`, authenticated `sender_route`, and requested `recipient_route`.
2. Find the server `send_settled` with the same `message_id` and sender/recipient route. Use its `request_id` and, when present, `delivery_id` to inspect transport-side outcomes.
3. Match route and public key across `relay_auth_accepted` or `relay_reconnect_succeeded` and server `auth_accepted`.
4. For an interruption, follow `relay_session_disconnected` to `relay_reconnect_scheduled`, `relay_reconnect_attempted`, and `relay_reconnect_succeeded`. `retry_index` is one-based and `delay_ms` is the actual jittered wait.
5. Share identifiers only with a trusted support channel. Never share pairing codes, the installation PEM, nonce, signature, or message content.

## Captured-stream acceptance

The primary diagnostics case in `extension/test/reconnect.acceptance.test.ts` builds and starts the real Go child, captures its stdout JSONL and stderr, and runs two extension instances behind `FakePiHost`. Native production `console.error` remains installed. The serial test temporarily captures the actual byte chunks passed to `process.stderr.write`, concatenates them before UTF-8 decoding, splits physical CR/LF framing, requires a final line terminator, then restores the exact write function. Any unrelated stderr output would fail the exact JSON-object parser rather than being relabelled as an extension event. The case crosses public pairing, authenticated WebSocket, model-tool, recipient Pi-injection, reconnect, heartbeat-control, and process shutdown boundaries.

The case extracts the raw startup pairing code and installation PEM from their private files. Its serial WebSocket observer pairs every real server challenge nonce with every hello signature from both subject and observer sockets before applying subject-specific retry controls. It requires one corresponding nonempty nonce/signature fixture for every observed hello. The same seam settles private string and object bodies as `received`, settles another private body as `timeout/offline`, rejects a hostile malformed destination without invoking its `toJSON`, forces two failed automatic attempts before a successful third retry under the existing fake clock, observes a real WebSocket pong as the heartbeat-control barrier, and then stops both Pi sessions and the server gracefully.

After child exit and `server_stopped`, the seam drains the server stdout readline iterator through confirmed EOF before parsing or scanning. Every captured nonempty normal line must parse as one non-array JSON object with no embedded physical newline; extension lines come from actual stderr bytes, not captured console arguments. Expected event schemas, available authentication request and sender-route correlation, severity, reconnect order, public-key visibility, message correlation, and literal redaction markers are asserted. No raw pairing code, PEM material, nonce, signature, hostile trap output, or body marker may be a substring of any server or extension line. The positive pong, settlement, reconnect success, session-stop, server-stop, and stream-EOF barriers make heartbeat silence and lifecycle completeness deterministic rather than timing-only negatives. A subordinate focused case proves ten failed retries emit one warning-level `relay_reconnect_exhausted` and create no eleventh retry.

<Decision title="Use logs only for relay v1 observability" status="accepted">
The operator-run relay has no demonstrated SLO, throughput, or cross-process complexity requiring OpenTelemetry. Relay v1 adds no metrics, traces, exporter, collector, health API, or dependency. Revisit only when measured operational needs cannot be answered from bounded structured events.
</Decision>
