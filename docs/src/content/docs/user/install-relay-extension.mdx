The extension exposes `list_peers` and `agent_send`. A connected Pi session authenticates one WebSocket automatically and receives its opaque route address. `list_peers` reads bounded live address-only roster pages; `agent_send` can deliver a provenance-labelled string or JSON object to an online idle or busy recipient and return extension-boundary `received`.

<Aside type="caution" title="Best-effort online delivery only">
A `relay_auth_accepted` diagnostic means the session connected and can use discovery plus successful idle and busy string/object delivery. Automatic reconnect can restore only that live capability. It does not enable offline delivery, replay, durable Pi acceptance, model completion, or guaranteed replies.
</Aside>

## Requirements

- Pi 0.85.1
- Node.js 24 or newer
- npm
- A trusted checkout of this repository
- A running Linux relay server
- One configuration file at `~/.config/pi/pi-messaging-relay.json`

The TypeScript extension remains a platform-neutral Node component; the Linux-only support boundary applies to the Go relay server because its state-directory safety depends on Linux filesystem semantics. Pi extensions execute with the user's full system permissions. Review `extension/index.ts` and its locked dependencies before installation. The extension pins `ws` v8.21.3 (MIT) for its bounded WebSocket transport and `typebox` v1.3.7 (MIT) for tool schemas.

## Install from a checkout

<Steps>
1. Install the extension's local runtime dependency from the lockfile:

   ```console
   $ npm --prefix extension ci
   ```

2. Write the client configuration file with mode `0600`. The path is fixed under your home directory — `XDG_CONFIG_HOME` is not honored:

   ```console
   $ install -m 0600 /dev/null ~/.config/pi/pi-messaging-relay.json
   $ vi ~/.config/pi/pi-messaging-relay.json
   ```

   Minimum content for an authentication-off server:

   ```json
   {"url":"http://127.0.0.1:8080"}
   ```

   With a secret-protected server, include the same secret the server reads from its secret file:

   ```json
   {"url":"http://127.0.0.1:8080","secret":"<REDACTED>"}
   ```

3. Load only this extension for one Pi invocation:

   ```console
   $ pi --no-extensions -e ./extension/index.ts
   ```

4. Confirm the connected address in the `relay_auth_accepted` diagnostic. A `relay_config_rejected` warning instead means the file was unreadable, unsafe, or rejected; the session stays disconnected.
</Steps>

## Configuration

The extension reads one closed JSON object from `~/.config/pi/pi-messaging-relay.json`:

| Member | Required | Meaning |
|---|---|---|
| `url` | Yes | HTTP loopback origin (for example `http://127.0.0.1:8080`) for a same-host relay, or an HTTPS origin (for example `https://relay.example.net`) for a remote TLS-terminating ingress. Plain HTTP stays loopback-only because it is unencrypted. The extension connects to the `/v1/connect` WebSocket path (`ws:` or `wss:` matching the scheme). |
| `secret` | No | Shared secret sent as `Authorization: Bearer <secret>` at the upgrade. Used verbatim with no trimming, 1–512 UTF-8 bytes. |

The file must be a current-user-owned regular non-symlink file with mode exactly `0600`. It holds at most 4,096 bytes of valid UTF-8. Duplicate keys, unknown keys, wrong types, trailing JSON, malformed UTF-8, and over-limit content reject the whole file.

`PI_MESSAGING_RELAY_URL` remains an optional override for the url only and is validated the same way. There is deliberately no secret environment variable: environment values are readable through `/proc` by same-user processes.

An absent config file with no environment override leaves the relay disconnected with no connection attempts. An invalid file — unreadable, unsafe form, wrong mode, or rejected JSON — is equivalent to absent: the extension never falls back to an unauthenticated default origin and never crashes the Pi session over it.

<Aside type="caution" title="Treat the config file as authentication material">
The optional `secret` is the only credential, exactly like a password. Never paste it into logs, shell history, chat, issue text, or screenshots, and never copy the file outside the owning user's home.
</Aside>

## Authentication modes

**Authentication off (default).** A server started without `--secret-file` accepts every upgrade regardless of headers. A config file with only `url` connects straight away. The relay still binds loopback only, which remains the primary boundary for this single-user scope; other local users and processes on the same machine can still reach the port.

**Secret mode.** A server started with `--secret-file` requires `Authorization: Bearer <secret>` on every `GET /v1/connect` upgrade. A missing header, wrong scheme, wrong secret, and over-limit value all receive the identical closed HTTP 401 with no upgrade. The extension then retries under the bounded reconnect policy until the configuration is corrected.

Rotating a secret means writing a new value into the server's secret file and restarting the server, then updating the client config file. There is no runtime rotation endpoint; a changed secret is one server restart plus one file edit.

To isolate a test configuration from your real home, point `HOME` at a scratch directory that also contains its own `~/.config/pi/pi-messaging-relay.json`.

After an attempt fails or an authenticated socket closes, automatic retries use a nominal 500 ms initial delay, multiplier 2, uniform ±25% jitter, a 30-second maximum actual delay, and at most ten retries for that uninterrupted failure sequence. Authentication success resets the progression. The active Pi session keeps its exact route UUID, cwd, hostname, and complete address throughout those attempts. A new or forked Pi session always gets a fresh route UUID. Reload and resume restore the current session route from hidden non-model session state when valid.

Extension JSONL diagnostics are written to the Pi process's stderr. Follow `relay_session_started`, `relay_auth_accepted`, and `relay_session_disconnected` with `relay_reconnect_scheduled`, `relay_reconnect_attempted`, and `relay_reconnect_succeeded`; `retry_index` is one-based and `delay_ms` is the actual jittered delay. Ten failed retries end with warning-level `relay_reconnect_exhausted`. Initial success remains `relay_auth_accepted`; automatic retry success uses only `relay_reconnect_succeeded`, avoiding a duplicate transition.

## Footer connection indicator

When an endpoint is configured, the extension renders one footer status line so you can see the connection state at a glance:

- **● relay (green circle)** — connected. The session can list peers and send messages.
- **● relay (red circle)** — not connected. This covers the initial connect attempt, reconnect retries under the bounded reconnect policy, an authentication rejection (closed HTTP 401), and a rejected configuration file.

The line shows a fixed `relay` label beside the circle, so the indicator never needs interpretation. When no endpoint is configured at all — no config file at all and no `PI_MESSAGING_RELAY_URL` override — the indicator is hidden entirely: nothing renders, not even a placeholder. An invalid or unsafe config file is a rejected configuration, not an absent one: it keeps the red indicator.

## Install as a local Pi package

For a self-contained store package, follow [Deploy with Nix](../nix-deployment/#install-the-extension-package). From a checkout, after `npm --prefix extension ci`, add the extension directory to user settings:

```console
$ pi install "$PWD/extension"
```

Pi reads the package manifest and loads `extension/index.ts` in future sessions. Deliver the config file at `~/.config/pi/pi-messaging-relay.json` the same way as above. The local-path installation references this checkout rather than copying it, so keep the checkout and its installed dependency available.

## Security

- The optional shared secret exists only in the config file and in process memory. It never appears in a notification, command output, or structured log; config diagnostics keep the `secret` field with the literal `<redacted>` value.
- Complete opaque route addresses, cwd, hostname, and correlation IDs remain visible for support correlation. They are not authorization evidence; the server authenticates only the configured upgrade secret.
- Message destinations are complete opaque addresses, never authorization components. A successful `received` means only that the intended extension attempted `pi.sendUserMessage`; message bodies are neither persisted nor logged. `relay_send_settled` describes the `agent_send` tool result with authenticated sender route, message ID, requested recipient route, status, reason, latency, and `body: "<redacted>"`; it does not claim stronger Pi receipt.
- A `list_peers` cursor is navigation only, not authorization. Copy only `next_cursor` returned by the relay; accepted cursors are at most 5,856 characters, and omitting one starts a fresh traversal. Roster pages are capped at 48 KiB for the complete WebSocket frame and contain only opaque addresses.
- Configuration failures do not invoke a model, inject a Pi message, or silently claim success. A rejected config file produces one closed warning and a disconnected session.
- The `url` scheme sets the trust boundary: plain HTTP is accepted only on loopback (`127.0.0.0/8`, `::1`) because it is unencrypted; HTTPS is accepted to any host because TLS protects the transport. Credentials, extra paths, query strings, and fragments fail closed for both schemes. For remote ingress, put the relay behind a TLS-terminating proxy you control (nginx allow-list, VPN, or SSH forward) and treat that proxy as the exposure boundary.
- Its pinned WebSocket client enforces a 512 KiB socket-wide ceiling before complete message delivery; hello and welcome messages keep a 16 KiB semantic ceiling. Shutdown requests graceful close for at most one second, then destroys and settles an unresponsive transport.
- The extension does not expose send transport request IDs or server-generated delivery IDs in its settlement event because the model-tool boundary does not own them. Match `message_id` and both routes to the server's authoritative `send_settled` when deeper transport correlation is needed.
- The relay emits logs only. It has no OpenTelemetry exporter, metrics endpoint, or traces. See [Structured relay diagnostics](../../developer/relay/structured-diagnostics/) for complete event schemas and support workflow.

## Troubleshooting

- **`Cannot find module 'typebox'` or `Cannot find module 'ws'`** — run `npm --prefix extension ci` from the repository root and keep `extension/node_modules/` beside `extension/index.ts`. This local package resolution is required for Nix-installed Pi too.
- **Command or tools absent** — confirm Pi loaded `extension/index.ts`; retry with the temporary `-e` command above and inspect Pi's extension issues.
- **`relay_config_rejected` at startup** — verify the file is the exact fixed path `~/.config/pi/pi-messaging-relay.json`, is a regular non-symlink file owned by the current user with mode exactly `0600`, holds at most 4,096 bytes of valid UTF-8, and contains only `url` plus optional `secret` with no duplicate or unknown keys. Fix the file and restart the Pi session; the extension never retries a rejected file mid-session.
- **`Relay is disconnected` despite a config file** — the rejected or absent file is equivalent to no configuration. Correct it and restart the session; the diagnostic `reason` distinguishes unreadable, unsafe-form, wrong-mode, and JSON rejections.
- **`url` rejected** — plain HTTP must use the exact numeric loopback origin printed in `server_ready`, for example `http://127.0.0.1:8080`. HTTPS must be the bare origin with no paths, query strings, credentials, or fragments. A remote relay over plain HTTP is rejected; use HTTPS or an SSH/VPN loopback forward.
- **`relay_auth_rejected` or bounded retries never succeed** — the server runs with a secret and the config file's `secret` is missing or wrong, or the server was restarted with a rotated secret while the client still has the old value. Write the matching current secret into the config file and restart the session. The relay deliberately returns the same closed 401 for every wrong credential spelling.
- **Connection drops after authentication** — the route disappears from live presence immediately. Wait for bounded automatic reconnect; the same complete address returns only after authentication succeeds. Ten exhausted retries leave the session disconnected until another session lifecycle starts a new sequence.
- **`list_peers` or `agent_send` reports a concurrent request** — wait for the existing outgoing operation to settle. The extension deliberately sends no second operation and creates no operation queue.
- **`agent_send` returns `timeout/offline`** — the exact destination is not currently published. The retained socket remains usable; refresh `list_peers` or send elsewhere.
- **`agent_send` returns `timeout/recipient_disconnected`** — lookup found the recipient, but the relay observed that exact session or offer write disappear before ACK. Every affected pending slot is released, the sender socket remains usable, and recipient reauthentication does not replay the interrupted offer.
- **`agent_send` returns `timeout/ack_timeout`** — the relay wrote the offer, but the exact recipient ACK did not arrive within five seconds. Pending capacity and both connections remain usable.
- **`agent_send` locally times out or disconnects** — the retained sender socket itself did not produce a valid correlated result. That operation is not resumed or replayed. Wait for automatic authentication restoration, then start a fresh tool call.
