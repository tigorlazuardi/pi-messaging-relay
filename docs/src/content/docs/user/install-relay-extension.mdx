The extension exposes `/relay-pair`, `list_peers`, and `agent_send`. A paired Pi session authenticates one WebSocket automatically and receives its opaque route address. `list_peers` reads bounded live address-only roster pages; `agent_send` can deliver text to an online idle or busy recipient and return extension-boundary `received`.

<Aside type="caution" title="Best-effort online delivery only">
An `auth_accepted` event means the session proved possession of an allowlisted installation key and can use discovery plus successful idle and busy text delivery. It does not enable offline delivery, replay, durable Pi acceptance, model completion, guaranteed replies, or reconnect.
</Aside>

## Requirements

- Pi 0.85.1
- Node.js 24 or newer
- npm
- A trusted checkout of this repository
- A running relay and its current operator-only pairing code

Pi extensions execute with the user's full system permissions. Review `extension/index.ts` and its locked dependencies before installation. The extension pins `ws` v8.21.3 (MIT) for its bounded WebSocket transport and `typebox` v1.3.7 (MIT) for tool schemas.

## Install from a checkout

<Steps>
1. Install the extension's local runtime dependency from the lockfile:

   ```console
   $ npm --prefix extension ci
   ```

2. Load only this extension for one Pi invocation, replacing the example address with the relay's `server_ready.address`:

   ```console
   $ PI_MESSAGING_RELAY_URL=http://127.0.0.1:43127 \
       pi --no-extensions -e ./extension/index.ts
   ```

3. In Pi, enter the current 32-character URL-safe code obtained from the server's private operator channel:

   ```text
   /relay-pair CODE
   ```

4. Confirm Pi reports the accepted public client identity. Do not copy the raw code into diagnostics. The code is consumed by that success and cannot pair a second installation.
</Steps>

## Configuration

| Environment variable | Required | Meaning |
|---|---|---|
| `PI_MESSAGING_RELAY_URL` | For pairing and connection | HTTP loopback origin, for example `http://127.0.0.1:43127`. The extension selects `/v1/pair` or the `/v1/connect` WebSocket. |
| `PI_MESSAGING_RELAY_STATE_DIR` | No | Installation-key directory. Default: `~/.pi/agent/pi-messaging-relay`. |

The endpoint must be an HTTP origin using a numeric loopback IP. Credentials, extra paths, query strings, fragments, HTTPS, hostnames, and non-loopback addresses fail closed. Use the localhost end of a trusted VPN or SSH forward for cross-machine operation.

The state directory must be owned by the current user with mode `0700`. The extension durably publishes `installation-ed25519.pem` with mode `0600` before contacting the relay, or safely loads an existing Ed25519 PKCS#8 key. The key is installation-wide and independent from per-session route IDs. Exactly two connection paths exist: pairing successfully during an already-started session causes one pairing-owned attempt, while pairing before lifecycle begins stores the key and the later `session_start` causes one startup-owned attempt. A missing key leaves startup disconnected without creating state. There is no reconnect or backoff yet.

To isolate a temporary test installation:

```console
$ install -d -m 700 /tmp/my-relay-extension-state
$ PI_MESSAGING_RELAY_STATE_DIR=/tmp/my-relay-extension-state \
    PI_MESSAGING_RELAY_URL=http://127.0.0.1:43127 \
    pi --no-extensions -e ./extension/index.ts
```

## Install as a local Pi package

After `npm --prefix extension ci`, add the extension directory to user settings:

```console
$ pi install "$PWD/extension"
```

Pi reads the package manifest and loads `extension/index.ts` in future sessions. Set `PI_MESSAGING_RELAY_URL` in the environment that launches Pi. The local-path installation references this checkout rather than copying it, so keep the checkout and its installed dependency available.

## Security

- The installation private key never leaves the extension directory and never appears in a notification or structured log. WebSocket authentication signs a fresh server nonce; nonce, signature, and private-key log fields always contain `<redacted>`.
- Pairing-code and private-key log fields retain their names but always contain `<redacted>`.
- Public key and accepted client ID may appear in logs for support correlation.
- The extension accepts only an exact 32-character URL-safe code. It rejects malformed or oversized command input locally before creating key state or contacting the relay; an accepted request is 126 bytes, below the 4,096-byte server limit.
- A syntactically valid code is usable only before its ten-minute deadline and only until its first successful pairing. The exact deadline is expired. Incorrect, expired, and reused codes all receive the same rejection and add no relay allowlist entry.
- The raw code is present in the localhost request because the relay must verify it. Pairing failure output omits the code entirely, and structured logs use `<redacted>` authentication fields rather than echoing the submitted or current value.
- The extension reads at most 4,096 pairing-response bytes, requires the JSON media type, rejects ambiguous response shapes, and accepts only `cli_` plus a 16-character URL-safe token as the client identity.
- Its pinned WebSocket client enforces a 512 KiB socket-wide ceiling before complete message delivery. During authentication, complete challenge and welcome messages still have a 16 KiB semantic ceiling. Shutdown requests graceful close for at most one second, then destroys and settles an unresponsive transport.
- Message destinations are complete opaque addresses, never authorization components. A successful `received` means only that the intended extension attempted `pi.sendUserMessage`; message bodies are neither persisted nor logged.
- A `list_peers` cursor is navigation only, not authorization. Copy only `next_cursor` returned by the relay; accepted cursors are at most 5,856 characters, and omitting one starts a fresh traversal. Roster pages are capped at 48 KiB for the complete WebSocket frame and contain only opaque addresses.
- Pairing failures do not invoke a model, inject a Pi message, or silently claim success.
- Never copy `installation-ed25519.pem`, the raw startup code, or their contents into an issue or chat.

## Troubleshooting

- **`Cannot find module 'typebox'` or `Cannot find module 'ws'`** — run `npm --prefix extension ci` from the repository root and keep `extension/node_modules/` beside `extension/index.ts`. This local package resolution is required for Nix-installed Pi too.
- **Command or tools absent** — confirm Pi loaded `extension/index.ts`; retry with the temporary `-e` command above and inspect Pi's extension issues.
- **Endpoint not configured or invalid** — set `PI_MESSAGING_RELAY_URL` to the exact numeric loopback origin printed in `server_ready`, with no `/v1/pair` suffix.
- **Unsafe state permissions** — verify the configured path is the intended dedicated key directory, then set its mode to `0700`; set the key file to `0600` only after verifying ownership.
- **Relay could not be reached** — verify the server is still running at the configured address and the ten-second request deadline was not exceeded.
- **Pairing code format rejected locally** — paste the exact 32-character URL-safe value with no surrounding whitespace. The extension has not created key state or contacted the relay.
- **Pairing code rejected by the relay** — the code was incorrect, reached its ten-minute deadline, or was already accepted once; the relay deliberately returns the same message for all three. Obtain a fresh code by restarting the server with a new unused private code-file path.
- **Authentication rejected after pairing** — confirm Pi still uses the state directory that owns the paired key and the same running relay process. Restart authorization acceptance belongs to ticket #27.
- **Connection drops after authentication** — the extension remains safely disconnected. Automatic reconnect and backoff belong to ticket #26; start a new Pi session or pair successfully during the current session for the currently supported one-attempt flow.
- **Pairing and authentication succeeded but `list_peers` says disconnected** — the retained socket closed or never authenticated. Start a new Pi session or pair successfully during the current session; automatic reconnect remains deferred.
- **`list_peers` or `agent_send` reports a concurrent request** — wait for the existing outgoing operation to settle. The extension deliberately sends no second operation and creates no operation queue.
- **`agent_send` times out or disconnects** — offline, missing-ACK, and recipient-disconnect machine results remain deferred. Start a newly authenticated session after the bounded local socket settlement.
