`agent_send` carries one string or JSON-object body to one authenticated Pi session that is online now. Get the complete destination from `list_peers` and copy it without splitting or editing it.

## Send and interpret the result

<Steps>
1. Call `list_peers({})` and select one complete `address`.
2. Call `agent_send` with that address as `to` and a string or JSON object as `body`.
3. Keep the returned `message_id` when you need to correlate relay logs.
4. Treat `status: "received"` only as an attempted recipient-extension injection.
</Steps>

The extension creates the message ID. Do not add `message_id`, delivery options, or steering fields to tool input. Every recipient sees a provenance header containing the complete quoted sender address and generated message ID. The extension treats that address as opaque; copy it whole. Delivery mode comes only from the recipient's current local state: an idle recipient gets `pi.sendUserMessage(rendered)` with no options, while a busy recipient gets `pi.sendUserMessage(rendered, { deliverAs: "followUp" })`. A follow-up waits behind all active recipient work; it does not steer or change the current run.

<Aside type="caution" title="Received is not completion">
`received` does not mean Pi persisted or queued the text, a model read it, work completed, or a reply will arrive. Relay restart, extension reload, process termination, or crash can lose downstream work.
</Aside>

## Current limits

This release completes successful idle and busy string/object delivery with deterministic provenance. String bodies are unchanged after the one LF that separates the header. Object keys are sorted recursively by JavaScript UTF-16 lexical order, including integer-like names; arrays retain their order and output is compact JSON. Replies (#17) remain unavailable: supplying valid `re` renders correlation but does not create or guarantee a reply. Offline destinations (#18), missing ACKs (#19), and recipient disconnects (#20) do not yet return their final machine-readable results; after five seconds the sender extension times out and closes its relay socket. Automatic reconnect is not available.

Only one `list_peers` or `agent_send` request may be active on one extension connection. A concurrent request fails locally without being queued. There is no transport retry, offline inbox, persistence, replay, broadcast, or delivery history. The final 256 KiB body rejection behavior belongs to #24; every complete transport frame is currently bounded to 512 KiB.

## Security and troubleshooting

Message bodies are not persisted or logged. Successful server telemetry includes public route, request, message, and delivery identifiers while the `body` field contains only `<redacted>`.

- **No result after a peer disappears:** current recipient-disconnect settlement is deferred. Wait for the bounded local timeout, then start a newly authenticated Pi session.
- **Disconnected error:** pair and authenticate the installation, or start a new Pi session if the retained socket closed. Reconnect is deferred.
- **Unsafe JSON object error:** use only JSON values in plain objects and dense arrays. Cycles, accessors, nonfinite numbers, `undefined`, bigint, symbols, functions, custom object prototypes, and malformed Unicode are rejected before transport without logging content.
- **Concurrent request error:** wait for the current list or send operation to settle; no request was queued.
- **Need proof of completion:** ask for a later ordinary reply after reply support lands. `received` is intentionally not proof of model work.
