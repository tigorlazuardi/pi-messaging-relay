`agent_send` carries one string or JSON-object body to one authenticated Pi session that is online now. Get the complete destination from `list_peers` and copy it without splitting or editing it.

## Send and interpret the result

<Steps>
1. Call `list_peers({})` and select one complete `address`.
2. Call `agent_send` with that address as `to` and a string or JSON object as `body`.
3. Keep the returned `message_id` when you need to correlate relay logs.
4. Treat `status: "received"` only as an attempted recipient-extension injection.
5. Treat `status: "timeout", reason: "offline"` as immediate current absence; the same connection remains usable.
6. Treat `status: "timeout", reason: "recipient_disconnected"` as relay-observed loss of the selected recipient session or failure to write its offer before ACK; the sender connection remains usable.
7. Treat `status: "timeout", reason: "ack_timeout"` as an offer written to a connected recipient that did not return the exact ACK within five seconds; both connections remain usable.
</Steps>

The extension creates the message ID. Do not add `message_id`, delivery options, or steering fields to tool input. Every recipient sees a provenance header containing the complete quoted sender address and generated message ID. The extension treats that address as opaque; copy it whole. Delivery mode comes only from the recipient's current local state: an idle recipient gets `pi.sendUserMessage(rendered)` with no options, while a busy recipient gets `pi.sendUserMessage(rendered, { deliverAs: "followUp" })`. A follow-up waits behind all active recipient work; it does not steer or change the current run.

<Aside type="caution" title="Results are current and best effort">
`received` does not mean Pi persisted or queued the text, a model read it, work completed, or a reply will arrive. `timeout/offline` means only that the exact opaque destination was not currently published when the relay looked it up; it does not reveal whether that route ever existed. `timeout/recipient_disconnected` means lookup found a recipient but the relay observed that exact session or offer write become unavailable before ACK. `timeout/ack_timeout` means the relay wrote the offer but did not receive matching delivery and message IDs from that exact recipient extension within five seconds. None is a model-read, completion, queue-durability, or message-durability status. Relay restart, extension reload, process termination, or crash can lose downstream work.
</Aside>

## Reply using the provenance header

An incoming message starts with a header like:

```text
[pi-messaging-relay] message from "/srv/frontend@workstation-a#01993ca1-1111-7aaa-8aaa-111111111111" (id=01993c84-fc2b-7e1c-af99-61b8118ac6df):
```

<Steps>
1. Copy the complete quoted `from` value, decode the displayed JSON string, and use that whole opaque address as `to`.
2. Copy the displayed `id` exactly and use it as `re`.
3. Call the same ordinary `agent_send({ to, body, re })` tool. Do not add `message_id`, request/delivery IDs, modes, or role fields.
4. Read the returned fresh `message_id` and status as the independent result for this reply only.
</Steps>

The extension generates a new reply message ID; it never reuses the original ID. The relay generates a new delivery ID and settles the reply independently from the original send. `re` is correlation metadata only: it does not authorize delivery, trigger a special reply operation, or prove that a retained original exists. The server performs no message-history or existence lookup. Replies are never automatic, and `received` guarantees neither completed work nor another reply.

## Current limits

This release completes successful idle and busy string/object delivery with deterministic provenance, ordinary correlated replies with fresh IDs and independent results, immediate `timeout/offline` settlement when the exact destination is absent from the current registry, `timeout/recipient_disconnected` settlement when the selected recipient session or offer write disappears before ACK, and `timeout/ack_timeout` settlement when a written offer receives no exact ACK within five seconds. String bodies are unchanged after the one LF that separates the header. Object keys are sorted recursively by JavaScript UTF-16 lexical order, including integer-like names; arrays retain their order and output is compact JSON. A registry miss creates no recipient offer, delivery ID, pending work, or history and does not close the sender connection. ACK timeout removes the pending offer before responding; a late ACK produces no response, cannot change the result, and does not damage the recipient connection. Disconnect cancellation releases every affected pending offer once. ACK, expiry, and disconnect compete for exact ownership, so a stale event cannot relabel the result. Reconnecting the same installation and address does not replay interrupted offers; stale ACKs are harmless, and only a fresh send creates a fresh offer. Automatic reconnect is not available.

Only one `list_peers` or `agent_send` request may be active on one extension connection. A concurrent request fails locally without being queued. After an offline, recipient-disconnected, or ACK-timeout result, use the same sender connection for `list_peers` or another send. The extension allows five seconds for a list response and eight seconds for a send response. The eight-second send deadline starts before relay processing and leaves room for the relay's bounded one-second recipient write, full five-second recipient ACK interval, bounded one-second sender response write, and scheduling. It does not reduce the recipient's five seconds. There is no transport retry, offline inbox, persistence, replay, broadcast, delivery history, or proof that an absent route existed before. The final 256 KiB body rejection behavior belongs to #24; every complete transport frame is currently bounded to 512 KiB.

## Security and troubleshooting

Message bodies are not persisted or logged. Server telemetry includes public route, request, and message identifiers while the `body` field contains only `<redacted>`. Successful delivery also includes a delivery ID. Offline settlement includes `status: "timeout"`, `reason`/`code: "offline"`, and the exact requested destination, but no delivery ID. Recipient-disconnect and ACK-timeout settlements include the generated delivery ID, `status: "timeout"`, and exact `reason`/`code: "recipient_disconnected"` or `"ack_timeout"`; stale competing events emit no second settlement.

- **Offline result:** refresh `list_peers` or choose another destination. The retained connection is still usable; retrying the same absent address does not create an inbox or history.
- **Recipient-disconnected result:** the relay found the listed recipient but observed its exact session disappear or could not write the offer before ACK. Every affected pending slot is released once. The sender socket stays usable; a later recipient connection receives no old offer.
- **ACK-timeout result:** the recipient was connected when the relay wrote the offer but no exact extension ACK arrived within five seconds. The pending slot is released and both sockets remain usable.
- **Disconnected error:** pair and authenticate the installation, or start a new Pi session if the retained socket closed. Reconnect is deferred.
- **Unsafe JSON object error:** use only JSON values in plain objects and dense arrays. Cycles, accessors, nonfinite numbers, `undefined`, bigint, symbols, functions, custom object prototypes, and malformed Unicode are rejected before transport without logging content.
- **Concurrent request error:** wait for the current list or send operation to settle; no request was queued.
- **Need proof of completion:** ask the recipient to send a later ordinary correlated reply. That reply is separate evidence, not a guarantee; either `received` result is intentionally not proof of model work.
