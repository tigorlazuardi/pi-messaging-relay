description: Use agent_send for best-effort text delivery that preserves a busy recipient's active work, without assuming completion or reply.

`agent_send` carries one text body to one authenticated Pi session that is online now. Get the complete destination from `list_peers` and copy it without splitting or editing it.

## Send and interpret the result

<Steps>
1. Call `list_peers({})` and select one complete `address`.
2. Call `agent_send` with that address as `to` and a text string as `body`.
3. Keep the returned `message_id` when you need to correlate relay logs.
4. Treat `status: "received"` only as an attempted recipient-extension injection.
</Steps>

The extension creates the message ID. Do not add `message_id`, delivery options, or steering fields to tool input. Delivery mode comes only from the recipient's current local state: an idle recipient gets `pi.sendUserMessage(text)` with no options, while a busy recipient gets `pi.sendUserMessage(text, { deliverAs: "followUp" })`. A follow-up waits behind all active recipient work; it does not steer or change the current run.

<Aside type="caution" title="Received is not completion">
`received` does not mean Pi persisted or queued the text, a model read it, work completed, or a reply will arrive. Relay restart, extension reload, process termination, or crash can lose downstream work.
</Aside>

## Current limits

This release completes successful idle and busy text delivery. The published schema reserves object bodies for final v1 compatibility, but this runtime rejects them locally before generating message identifiers or sending a frame. Use a text string until provenance headers and deterministic object formatting land in #16. Replies (#17) remain unavailable. Offline destinations (#18), missing ACKs (#19), and recipient disconnects (#20) do not yet return their final machine-readable results; after five seconds the sender extension times out and closes its relay socket. Automatic reconnect is not available.

Only one `list_peers` or `agent_send` request may be active on one extension connection. A concurrent request fails locally without being queued. There is no transport retry, offline inbox, persistence, replay, broadcast, or delivery history. The final 256 KiB body rejection behavior belongs to #24; use short text in this release.

## Security and troubleshooting

Message bodies are not persisted or logged. Successful server telemetry includes public route, request, message, and delivery identifiers while the `body` field contains only `<redacted>`.

- **No result after a peer disappears:** current recipient-disconnect settlement is deferred. Wait for the bounded local timeout, then start a newly authenticated Pi session.
- **Disconnected error:** pair and authenticate the installation, or start a new Pi session if the retained socket closed. Reconnect is deferred.
- **Object-body unsupported error:** submit a text string instead. The object was not sent, the body was not logged, and the retained connection remains usable.
- **Concurrent request error:** wait for the current list or send operation to settle; no request was queued.
- **Need proof of completion:** ask for a later ordinary reply after reply support lands. `received` is intentionally not proof of model work.
