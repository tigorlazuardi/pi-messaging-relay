<Aside type="caution" title="Linux-only relay server">
The Go relay server is supported only on Linux. Its state-directory safety requires Linux descriptor-relative filesystem operations, no-follow opens, Unix ownership, and Unix mode bits. Non-Linux builds refuse startup instead of using a weaker storage path. The separately installed TypeScript extension is not restricted by this server build boundary.
</Aside>

The relay binds only to a loopback IP literal. Authentication is optional and off by default: without a secret file the server accepts every upgrade and still binds loopback only. With `--secret-file`, every `GET /v1/connect` upgrade must carry `Authorization: Bearer <secret>`.

## Build and start

<Steps>
1. From the repository root, build the command:

   ```console
   $ mkdir -p bin
   $ go build -o bin/pi-messaging-relay-server ./cmd/pi-messaging-relay-server
   ```

2. Create the state directory. It is required when enabling authentication, because the secret file must live directly inside it:

   ```console
   $ install -d -m 700 "$HOME/.local/state/pi-messaging-relay"
   ```

3. **Authentication off (default):** start the server without `--secret-file`:

   ```console
   $ ./bin/pi-messaging-relay-server \
       --state-dir "$HOME/.local/state/pi-messaging-relay"
   ```

   **Secret mode:** generate a secret, write it into a new direct child of that state directory, and point `--secret-file` at it:

   ```console
   $ umask 077
   $ head -c 32 /dev/urandom | base64 > "$HOME/.local/state/pi-messaging-relay/relay-secret"
   $ chmod 600 "$HOME/.local/state/pi-messaging-relay/relay-secret"
   $ ./bin/pi-messaging-relay-server \
       --state-dir "$HOME/.local/state/pi-messaging-relay" \
       --secret-file "$HOME/.local/state/pi-messaging-relay/relay-secret"
   ```

4. Read the first `server_ready` JSON line. Its `address` field is the listener origin and its `auth` field reports the active mode: `"off"` or `"secret"`. Verify the mode from this field instead of from connection probes.
</Steps>

<Aside type="caution" title="Treat the secret file as authentication material">
Do not paste the secret into logs, shell history, chat, issue text, or screenshots. The server never logs it. The file must be a direct child of the active state directory, owned by the current user, a regular non-symlink file with mode exactly `0600`, and 1–512 UTF-8 bytes after surrounding whitespace trimming.
</Aside>

<Aside type="note" title="Auth-off still means loopback-only">
Authentication-off is the single-user default: no secret to lose, no config to get wrong. The relay never leaves the loopback interface, so cross-machine operation still requires a trusted VPN or SSH loopback forward. Other local users and processes on the same machine can connect while authentication is off.
</Aside>

## State and secret file

| Flag | Behavior |
|---|---|
| Omit `--state-dir` | Create unique temporary state and remove it on graceful shutdown. Because its random path is not known before startup, no configured secret file can be its direct child; authentication is off for that startup. |
| `--state-dir PATH` | Create or use a mode-`0700` durable directory. Required with `--secret-file`. |
| Omit `--secret-file` | Start with authentication off: every upgrade attempt is accepted regardless of headers, and no Authorization value is inspected. |
| `--secret-file PATH` | Read the shared secret from a mode-`0600` current-user-owned regular non-symlink direct child of the active state directory. External, parent-traversing, root, and state-root paths fail before readiness. |

The server opens the secret file nonblocking through the retained state-directory handle without following symlinks, reads at most 4,096 bytes, requires valid UTF-8 with no NUL byte, trims surrounding ASCII whitespace, and requires a non-empty result of at most 512 UTF-8 bytes. The secret is retained only in process memory, is never logged, and structured events keep any authentication field name with the `<redacted>` value.

A set-but-broken secret — invalid path, unsafe file form, wrong mode, wrong owner, unreadable content, empty or over-limit value — fails startup before `server_ready` and never silently degrades to authentication off.

There is no runtime rotation endpoint. Rotating the secret means rewriting the file with mode `0600` and restarting the server; the restart reads the file once. Clients whose config file still carries the previous secret then receive the closed 401 rejection until they are updated.

Linux path trust covers the complete absolute path, not only its last component. Every ancestor must be owned by root or the relay process user. Group- or other-writable ancestors must also be sticky; `/tmp` mode `1777` is the normal accepted shared-directory example. Any ancestor symlink or writable non-sticky ancestor fails before `server_ready`. After validation, the process keeps the opened directory handle and performs secret-file operations relative to it. Renaming or replacing the configured pathname cannot redirect secret reading while that process runs.

Every structured stdout or stderr event has a one-second delivery deadline, and every HTTP response write has a two-second deadline. Normal server lifecycle, authentication, protocol, and settlement JSONL goes to stdout. Only fatal `server_failed` goes to server stderr. The Pi extension independently writes its JSONL diagnostics to the Pi process's stderr. A stopped log reader or non-reading local client therefore cannot retain request handling indefinitely. If stdout cannot record a settled authentication or settlement event, the process stops accepting work, drains for at most five seconds, attempts `server_failed` on stderr, and exits non-zero even when SIGINT or SIGTERM arrives concurrently.

## Migrating from protocol v1

Protocol v2 deliberately breaks v1 deployments; there is no compatibility mode and **no automatic migration**. What stopped existing:

- The `/relay-pair` Pi command and the server's `POST /v1/pair` endpoint. The server answers `POST /v1/pair` with the ordinary not-found path; no shim exists.
- Startup pairing codes and the `--pairing-code-file` operator channel.
- Ed25519 installation keys (`installation-ed25519.pem`), client identities, and the persisted `allowlist.json`.
- The nonce challenge and the signed hello transcript.

A v1 extension cannot authenticate to a v2 server and a v2 extension cannot authenticate to a v1 server; mismatched deployments fail closed at the boundary in both directions.

What to do instead:

1. Start the server with `--secret-file` pointing at a mode-`0600` direct child of its state directory (or deliberately stay authentication-off).
2. Write the client config file at `~/.config/pi/pi-messaging-relay.json` with mode `0600`, holding `url` and, when the server has a secret, the same `secret`.
3. Remove `installation-ed25519.pem`, `allowlist.json`, and any `/relay-pair` usage from scripts and documentation. Nothing persists to re-run after a restart beyond the secret files.

<Aside type="caution" title="No automatic migration">
The accepted contract removes pairing, installation keys, and the allowlist outright, not behind a flag. Deployments migrate by provisioning the two secret files and updating the client configuration; every existing v1 credential becomes inert.
</Aside>

## Session and delivery limits

`/v1/connect` reserves one of 1,024 tracked session slots before WebSocket upgrade and reads the unsigned hello within a five-second establishment deadline shared with the welcome write. At capacity, it returns HTTP `503` without upgrading and emits `session_capacity_rejected`. With a secret configured, the upgrade authorization runs first and a rejected request consumes no tracked slot. An active duplicate route UUID or opaque address is rejected and closed without a welcome; the composite address is never parsed for authorization. Graceful shutdown force-closes and settles every reserved or upgraded socket before `server_stopped`.

After authentication, each complete WebSocket message has a 512 KiB ceiling across all fragments. A send's serialized JSON body value has a separate 256 KiB (262,144 UTF-8-byte) ceiling that includes string quotes/escapes and object syntax. Only text containing one valid UTF-8 JSON object is accepted. `invalid_frame`, `invalid_envelope`, and `unsupported_protocol` errors set `close: true`. On detection, the relay immediately removes that session from new routing, lets an already-writing offer finish before completed removal but rejects any queued or preselected offer afterward, drops queued ordinary responses, attempts one bounded error response, and hard-closes; a malformed frame may close before the error arrives. Operation-level outcomes are different: they return a normal result and keep the session open. Live `list`/roster discovery, up to 128 in-flight distinct sends per exact authenticated sender session, recoverable `denied/sender_capacity` and `denied/body_too_large`, successful authenticated delivery, immediate `timeout/offline`, `timeout/recipient_disconnected`, and five-second `timeout/ack_timeout` are available. These normal results leave the sender socket reusable.

The extension keeps one outgoing list/send operation active per connection and adds no queue. Before owning an operation, it validates the 256 KiB body budget. Raw authenticated clients may pipeline sends. Strict protocol and body checks run first, then dedupe observation; only a legal new logical send attempts one of 128 nonblocking slots for that exact authenticated sender session. At 128, the next distinct send receives correlated `denied/sender_capacity` without recipient lookup, delivery ID, pending state, timer, dedupe record, or close. A later use of that denied message ID is new after capacity releases, and another authenticated sender session has independent capacity.

The relay releases a responding send slot only after the original and optional attached-retry results own bounded response sequencing and are ready for serialized publication; cancellation or disconnect with no response releases immediately. Each exact authenticated session reserves from 256 normal-response positions before encoding, so no more than 256 unanswered encoded normal results exist there; a terminal protocol error is one separate bounded result. Settlement, ACK timeout, and recipient disconnect therefore restore slots. Sender disconnect abandons all exact-session work without public results. Lists and response-free ACK candidates execute one at a time in the reader, may overlap sends, consume no SEND capacity, and have no server-side queue. Reconnected recipients receive no interrupted offer.

For deduplication, each exact recipient session retains at most 1,024 settled `received` or `ack_timeout` message IDs in oldest-settled insertion order. Entry 1,025 evicts entry 1. Retained identical IDs return their known result; destination, reply correlation, or semantic body changes return recoverable `denied/message_id_conflict`. Separately, each exact sender session keeps at most its one current logical result across recipient cleanup so an already-emitted retry cannot become a new offer after the destination reconnects. This includes current `offline` and `recipient_disconnected` results. It clears after retry classification, the next distinct list or send, exact sender loss, or shutdown. Nothing persists, transfers to a sender reconnect, or replays an old offer. A replacement process emits no pending, settled, startup-history, or interrupted delivery when clients reconnect; only a fresh send creates the next offer.

The authenticated `list` payload is exactly `{}` for a fresh first page or `{"cursor":"..."}` for continuation. A cursor is `cur_` plus canonical unpadded Base64url of the previous page's last opaque address, up to 5,856 characters. Malformed, padded, noncanonical, invalid-UTF-8, duplicate, mistyped, unknown-field, and over-limit cursor input returns terminal `invalid_envelope`; cursor content never grants authorization. A valid request reads current authenticated sessions and returns a live lexicographic address-only page. Complete roster frames are capped at 49,152 bytes, and the server retains no pagination snapshot.

Ponytail: event delivery is fixed to one second, the secret-file read to 4,096 bytes and the secret to 512 bytes, secret rotation to restart-only, authentication and recipient ACK to five seconds, the one extension retry trigger to four seconds from logical-operation start inside an eight-second send deadline, hello frames to 16 KiB, serialized JSON body values to 256 KiB, post-authentication messages to 512 KiB, roster frames to 48 KiB, cursors to 5,856 characters, retained settled IDs to 1,024 per exact recipient session, sender-current results to one per exact sender session, in-flight sends to 128 and response ownership to 256 per exact authenticated session, tracked sessions to 1,024, response writes to one second for authenticated WebSockets and two seconds for HTTP, and shutdown drain to five seconds.

## Correlate diagnostics safely

Start from the extension's `relay_send_settled.message_id`, authenticated `sender_route`, and requested `recipient_route`. Find the server stdout `send_settled` with that message ID; it adds the transport `request_id` and, when an offer existed, the server-generated `delivery_id`. Match route across extension `relay_auth_accepted`/`relay_reconnect_succeeded` events and server `auth_accepted`; post-hello rejected server authentication events also retain the hello request ID when available. Upgrade rejections happen before any WebSocket exists and publish no request ID.

Logs keep complete opaque routes, cwd, hostname, and correlation IDs visible. They replace every authentication field — including the shared secret and message bodies — with literal `<redacted>`. Do not attach the server secret file, client config file, transport captures, or message text to a support report. WebSocket ping/pong heartbeat control traffic is deliberately silent at normal log levels. The relay has no OpenTelemetry, metrics, or traces. Full event schemas: [Structured relay diagnostics](../../developer/relay/structured-diagnostics/).

## Select a port

Pass a loopback IP literal and port with `--listen`:

```console
$ ./bin/pi-messaging-relay-server --listen 127.0.0.1:8080 --state-dir "$HOME/.local/state/pi-messaging-relay"
```

IPv6 loopback is also accepted, for example `--listen '[::1]:8080'`. Hostnames such as `localhost`, wildcard addresses such as `0.0.0.0`, and non-loopback IPs are rejected.

<Aside type="caution" title="Local transport only">
Do not treat this process as a public internet endpoint. Built-in TLS and public listener support are outside the relay contract. Cross-machine operators must provide a trusted VPN or SSH loopback forward; the optional secret defends only the loopback port against other local users and processes.
</Aside>

## Stop cleanly

Send SIGINT with <kbd>Ctrl</kbd>+<kbd>C</kbd>, or send SIGTERM from a process supervisor. A successful stop releases the listener, removes temporary state, retains explicit durable state, and exits with code `0`. The secret file is operator-owned input and is left in place.

## Security checks

- Keep the server listener on `127.0.0.0/8` or `::1`; never place it directly on a LAN or public interface.
- When authentication is off, remember that any local user or process on the machine can connect to the loopback port. Enable a secret when that exposure matters.
- Keep the final state directory owned by the relay process user; startup rejects a different owner. Keep every ancestor owned by root or that user, and remove group/other write permission unless the shared ancestor intentionally uses the sticky bit.
- Do not put state below a symlinked ancestor. Resolve deployment paths structurally instead of relying on `readlink` output or a one-time canonicalized string.
- Do not weaken `0700` state-directory or `0600` secret-file modes, change the secret file's ownership, or replace it with a symlink or other file type.
- Place `--secret-file` directly inside the exact state directory as shown above. This is mandatory: every external parent, `..` parent traversal, root form, or state-root target is rejected before readiness. Creation-time validation and reading use the retained directory handle and cannot be redirected by later pathname replacement.
- Never pass the secret through argv, environment, Nix options, or the Nix store; the only supported channels are the mode-`0600` server secret file and the mode-`0600` client config file.
- Structured logs may contain display route metadata, but secret and body fields must remain `<redacted>`.

## Troubleshooting

- **`listen: bind: address already in use`** — choose another fixed port or use port `0`.
- **`listen address must use a loopback IP literal`** — use `127.0.0.1` or `::1`, not a hostname, wildcard, LAN, or public address.
- **`durable state directory must be ... 0700`** — make the dedicated directory private with `chmod 700 PATH`, after verifying it is the intended relay directory.
- **`durable state directory must be owned by the current user`** — run the relay as the directory owner or select a dedicated mode-`0700` directory owned by that process user. Do not change ownership without first verifying the exact path.
- **State ancestor rejected** — remove symlinks from the entire selected path. Ensure each ancestor is root-owned or owned by the relay user; remove group/other write permission, or set the sticky bit only when that ancestor is intentionally shared and its sticky-directory semantics are understood.
- **Linux-only startup refusal** — run the server binary on Linux. Do not bypass the refusal or copy the state safety into an unvalidated non-Linux implementation.
- **`server secret file must be a direct child of the state directory`** — provide an explicit `--state-dir`, then place the secret file immediately inside that exact directory. Remove parent traversal and do not use an external directory, the state path itself, or the filesystem root.
- **Secret permission or ownership failure** — verify the file is owned by the current user and set `chmod 600 PATH` after verifying it is the intended secret file. Never weaken the check or substitute a world-readable location such as a Nix store path.
- **Secret content failure** — the file must decode as UTF-8 with no NUL byte and hold 1–512 bytes after trimming. Rewrite it and restart.
- **Clients receive 401 after a server restart** — the secret file content changed (rotation) or the server started with a secret while clients still send none or the wrong one. Rewrite the client config files to match, or deliberately remove `--secret-file` to return to authentication-off.
- **No `server_ready` event** — inspect the structured `server_failed` event on stderr. The process exits non-zero when startup cannot complete.
- **`invalid_frame` followed by disconnect** — the client sent binary data, invalid UTF-8, malformed or trailing JSON, or more than 512 KiB in one reassembled message. Fix framing before reconnecting; fragmented messages share the same total ceiling.
- **`invalid_envelope` followed by disconnect** — the JSON object had duplicate or unknown fields, a missing or mistyped operation field, an invalid UUIDv7 or list cursor, or a server-to-client/unknown type. Do not retry the same envelope unchanged.
- **`unsupported_protocol` followed by disconnect** — the client's integer protocol major is not `1`. Use a compatible client.
- **Operation denial without disconnect** — expected for a structurally valid request rejected by an operation handler. `body_too_large` means the trimmed serialized JSON body value exceeded 262,144 UTF-8 bytes; it is rejected before destination lookup, so telemetry omits recipient route and delivery ID while retaining `body: "<redacted>"`. `message_id_conflict` means one authenticated sender session reused a retained logical ID with changed destination, `re`, or semantic body. `sender_capacity` means that exact sender already owned 128 in-flight distinct sends; wait for settlement, timeout, recipient disconnect, or use a different independently authenticated sender session. Capacity denial performs no recipient lookup, so telemetry omits recipient route and delivery ID. The same authenticated socket remains usable; raw bodies and fingerprints never enter logs.
- **`fatal relay runtime failure`** — a live-session audit event could not reach stdout. Repair or redirect the broken or unread destination before restarting. If stderr is also blocked, its failure event is bounded and may not reach the operator before exit.
